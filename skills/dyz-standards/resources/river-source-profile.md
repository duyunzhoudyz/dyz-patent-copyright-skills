# River来源关系与待审附录／RS-RIVER-2

这是[River三案](river-example.md)现有T/CAICI内部草稿的新增资料性附录，结合[2026-11-03来源补核](../../../references/standards/river-source-evidence-20261103.md)使用。原N／C／V正文、需求、模型及58向量保留，不把此次取得来源追记为旧稿当时已读；本附录不替换原稿第2章，也不引入新的规范性引用或正式标准编号。

## 1. 对引用与正文的具体审阅建议

RFC 8259可列为JSON技术比较的资料性文献。拟将其升为新稿规范性引用时，先由技术责任人决定采用的版本、勘误处理和具体依赖，明确本接口是严格应用约束，另行重建正文、引用表、验证计划及文件。GB/T 1.1-2020仍只有目录记录，本附录不作其格式或全文符合性判断。

“合法JSON”“满足River约束”“实现互操作”“组织审查通过”分别判断。现有模型的`json`原因码同时包含通用语法错误及接口禁止的数字／重复名，不能将这一原因码解释成“RFC判定非法”。它只是R09指定的本地逻辑类别。

可供下一稿审阅的说明文字为：本接口按给定的对象结构与字节预算接收JSON消息，并额外限制数字词法、重复成员、标识及状态行为；这些选择来自RQ-RIVER需求。其数值预算、记录数和重放政策不是RFC给出的普遍阈值。这个说明不改变任何既有RIV要求，也不声称通用JSON解析器可以拒绝所有其他合法JSON。

## 2. 来源—选择—条款—输入

RFC位置均指原始2017文本；5318争点另记，不把原文和勘误拼成未标识的新版本。下表“已有”编号来自原58向量，“新增”来自[边界输入](river-demo/source-boundary-vectors.json)，预期与实际结果分开保存。

## 3. 可复核的执行办法

Python 3.11标准库，在仓库或完整本地包根执行：

```powershell
python -X utf8 skills/dyz-standards/resources/river-demo/model.py
python -X utf8 skills/dyz-standards/resources/river-demo/model.py skills/dyz-standards/resources/river-demo/source-boundary-vectors.json
```

这两个命令只读取本地文件并向标准输出打印JSON，不启动服务或写文件。第一条运行原58项，第二条运行新增16项；第二条的相对向量路径以当前工作目录为准。报告列环境、实际源文件SHA-256、输入字节数／哈希、初始状态对应预期、实际状态、调用者状态是否被改动及失败项。命令不联网取RFC，包内也不携带第三方原文。包搬迁后须从新包内运行并核报告源路径，不能借用源仓库运行成绩。

新增预期是在阅读既有实现及来源后、首次执行这组输入前冻结，属于作者开发验证。不得称为先于原模型设计、盲测、第二实现或专业复核。RFC关系分类是有来源的人工待审判断，不由被测模型或Python默认`json.loads`充当独立真值。SB-13的争议状态必须保留，即使River结果与预期一致。

报告的`fixture_id`沿用原模型标识`deepening-standards-d3`；本次究竟读了原58项还是新增16项，应以`sources`中的向量文件名及实际SHA-256核对，不能只凭这个模型标识复用旧结果。
