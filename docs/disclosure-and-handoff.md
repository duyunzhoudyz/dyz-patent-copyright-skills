# 跨子系统交接、披露审批与事件处置设计

日期：2026-10-31。状态：已有本地合成执行与验证的契约。共享core/disclosure/cli实现固定快照、权限/版本/依赖检查、SQLite审批记录与一次合成执行/回执/unknown暂停/事件闭环；预览双输出及外置旁证重验已接入。未实现真实出口隔离或自动专业审批，身份与专业签核未验证。本文DG保留完整验收目标，已有合成分支通过不等于真实环境全部通过。总体职责见 [能力蓝图](capability-blueprint.md)，能力规格见 [能力契约](capability-contracts.md)，实施阶段见 [路线与质量门槛](roadmap-and-quality.md)。

## 1. 目标、边界与默认原则

同一技术方案可用于专利、软件版权和技术标准，但共享原始证据不合并三条业务的状态、权利或公开范围。本流程覆盖内部跨业务使用、外部受控共享、服务商处理、公开披露和正式提交；这些是不同权限，不是一张“同意使用”概括授权。

- 对拟保留专利机会的未公开内容，先核实实际申请事实、原始公开支持及目标地区安排，再决定是否披露；已有申请号不是全部内容可公开的证明，起草完成也不等于已经提交。
- 不以等待授权作为统一条件，也不以各地宽限期或例外作为默认补救。是否充分公开、享有何日优先权及具体法律后果，交由适用地区专业审阅；已有官方来源分级索引但均未专业核验，不设全球统一安全期限。
- 判定对象是具体内容及其组合，不只检查单个关键词；专利依据包括实际提交的说明书、权利要求和附图，不限于权利要求。
- 外发不必然是公开。受控共享须核实合同、访问及传播条件；登录、工作组身份、口头称“内部”都不直接证明保密性。
- 已公开内容也要核实来源、时间、第三方权利和再分发权限。合法取得标准或源码不等于允许上传云模型、复制全文或公开译文。
- 有意防御性公开是单独的策略路线：明确可能放弃的机会、其他权利和剩余风险，由有权人批准；不得沿用“专利保护已落实”的结论。审批不能豁免法律、强制程序或第三方权利。
- 标准组织的必要声明和其他义务按适用政策处理；保密控制不能用于隐瞒必须披露的信息，也不能因此无必要公开完整交底书。两者冲突时列为待专业决策事项，不自动选择一边。

## 2. 所有权与两条独立交接

共享CORE-04/06维护权限、审批对象及执行记录；各专业维护判断、规则和业务状态。交接不创建第四个专业子系统，也不复制一套SEP分析器。

| 交接路径 | 发起与接收能力 | 专业输出 | 不得混同 |
| --- | --- | --- | --- |
| 标准或源码拟披露未公开技术 | STD-08或SW-03/07，经CORE-04/06交PROC-01/02、ANALYSIS-05、REVIEW-02 | 内容—实际申请原文—相关日期—目标地区的支持与公开风险意见 | 申请号、文字相同、同族关系都不自动证明支持或有效日期 |
| 标准专利政策、必要性及许可 | STD-08分别交RIGHTS-07、RIGHTS-03/06 | 组织政策与声明准备；必要性、FTO和许可问题分别处理 | 引用或声明不等于SEP、许可承诺不等于已获许可，自己有专利不等于FTO通过 |
| 软件材料转登记或外部审阅 | SW-01/03/07，经CORE-04/07 | 主张范围、例外交存、权利限制及获准版本 | 登记提交、代理师审阅和公开源码是不同用途 |
| 通用编辑、翻译、制图后的回交 | REVIEW-05/06、FIG及工具返回原专业 | 语义差异、支持／软件事实／条款判定影响、重新签核 | 工具完成不等于专业通过；译文和图片也可能新增披露 |

### 责任与签核

| 角色 | 必须确认 | 权限边界 |
| --- | --- | --- |
| 技术负责人 | 内容真实性、技术要素及组合、隐藏信息、与基线差异 | 不以技术熟悉程度替代专利或权利判断 |
| 专利专业审阅者 | 实际提交文件、相关日期、原始支持、目标地区和保密／涉外条件 | 资格与委托按任务核实；不代权利人批准公开 |
| 软件版权专业审阅者 | 软件／版本／主张关系、第三方和人类贡献、交存及处理权限 | 仅涉及软件材料时适用，不为所有标准任务强制增加角色 |
| 标准负责人 | 接收组织、阶段、传播规则、政策和声明／签署条件 | 不能用项目立项或内部核稿代替公开许可、共识或组织批准 |
| 材料与隐私责任人 | 材料权利、保密约束、服务商处理、访问范围、保留要求 | 获取权、处理权、再分发权分别确认 |
| 权利人或授权批准人 | 具体动作授权、剩余风险及策略取舍 | 权限有依据；不能以风险接受消除第三方限制或虚构确定性 |
| 外发执行器或人工执行人 | 固定版本、目的地、权限、有效期、实际执行与回执 | 不改变审批对象，不自行作专业结论或代签 |

每次审批列明必需角色及不适用角色的理由。小团队可一人多角色，但逐项确认；需要独立审阅的任务不能以模型互评冒充独立有权签核。缺有权人或必要专业判断时，允许保存草稿，不允许标为可执行。

## 3. 最小交接数据契约

现有合成实现使用本地JSON及SQLite journal，不要求外部数据库、服务或电子签章平台。以下保持业务设计字段；可执行参数以共享SKILL为准，本次只同步文档，不创建schema、空记录或新实现。证据ID与哈希指向获准存储，公开仓库不保存案件正文。

| 记录 | 最小字段 | 维护者与约束 |
| --- | --- | --- |
| 关联项目与技术基线 | project_id；各业务record_id；版本／哈希；技术特征及组合ID；已公开、未公开、第三方分类；贡献与权属证据 | 各业务分别维护事实，CORE关联；共享ID不合并状态 |
| 披露请求 | release_id；目的；动作类别；接收组织／人员／服务；渠道；计划时间与时区；访问、下载、转发、归档、保留和费用条件 | 发起业务；渠道标“内部”不是保密证据 |
| 内容支持映射 | 文件／条款／附件位置；特征及组合；实际申请文档ID及位置；相关日期及依据；目标地区；映射理由、未知项和审阅者 | 专利侧；每项区分支持已确认、新增内容、待判断、不适用及理由 |
| 申请事实包 | 官方提交记录；实际提交文件清单及哈希；申请标识；日期证据；优先权／后续路线；核验时间与状态 | PROC侧；提交回执与取得有效申请日不是可任意互换的事实 |
| 材料使用权清单 | 材料ID；获取、模型处理、复制、翻译、公开再分发权限；合同／许可依据；地域、期限、保密及保留条件 | 原业务与材料责任人；未知不自动变为允许 |
| 候选外发包 | manifest_id；全部文件及附件哈希；源版本；语义差异；元数据／隐藏内容检查；未解决项 | CORE-07生成、专业复核；正文、内部风险报告分开，后者不默认随包发送 |
| 审批记录 | decision_id；release_id；包／映射／规则／申请证据版本；动作、对象、用途、渠道；必需签核；权限依据；条件、有效期、次数；撤销／失效原因 | CORE-06保存，专业人判断；同意受控共享不授权公开 |
| 执行记录 | execution_id；审批ID；发送前复核；实际版本、对象、时间与访问配置；尝试状态；回执；核实结果 | CORE-04执行层；失败、结果不明、已发送分开 |
| 事件记录 | incident_id；发现时间；关联包／动作；已知可访问范围及时间；证据保全；止损操作及授权；通知、专业评估和后续决定 | CORE与受影响专业共同维护；不回填审批掩盖误发 |

“支持已确认”仅针对已审核事实、地区和版本，不代表保证授权或所有未来公开安全。记录真实时间与时区，法律上如何适用“日”或其他期限由专业规则判定，不能自行用时间戳比较代替。

## 4. 八步工作流

### 4.1 冻结受控基线

关联三业务记录，确定技术特征及组合、代码、图、参数、试验和已有公开证据。先检查运行环境和资料权限，再读取敏感材料；禁止先上传给模型、再补同意。

### 4.2 提出披露请求

标准提案、会议演示、征求意见、邮件审阅、软件交存、平台上传等都需明确动作及范围。记录会议录制、公开归档和链接权限扩大等后续条件。内部跨业务使用只请求必要权限，不自动触发对外发送。

### 4.3 建立内容与申请支持映射

对正文、编制说明、演示、附件、试验方法、数据、代码和图片一并审查；分析多份材料组合后的可推导信息。冻结实际提交版本，不能用尚未提交的内部新稿补足旧申请依据。

未覆盖内容可删去／暂缓、先安排适当后续申请后重审，或在经核实且批准的限制下共享。有意公开走单独策略；新增内容不得自动继承旧日期，补申请亦不能倒置已发生的公开事实。

### 4.4 核实申请、权利与接收条件

核对实际文件、官方记录、日期、相关地区安排、材料权利、组织政策和其他限制。对于没有专利保护目标或确属已公开的内容，记录不适用理由及证据，不强迫虚构一份专利申请。任何必要判断未知时，不能标为专业通过。

### 4.5 生成最小必要外发包

从受控版本生成独立包；检查修订、批注、属性、隐藏表、演示备注、嵌入对象、图片文字、文件名、路径、内部链接及日志。清理后重新验证可实施性和语义，不以脱敏制造不完整或误导性标准条款。更改包必须重新计算哈希和影响范围。

### 4.6 对具体包签核

必需角色完成各自判断后，有权人批准特定版本、对象、动作和条件。决策类型区分“公开许可”“受控共享许可”“服务商处理许可”“正式提交许可”；条件许可必须在执行前证明条件已满足，不是自动放行。

### 4.7 发送前复核并记录执行

执行时重新验证哈希、对象、访问配置、审批有效性及未撤销状态，只读取已批准的固定字节，不在审批后重新生成文件再发送。本地合成实现从已校验的固定snapshots取字节，当前依赖与审批绑定变化时拒绝，不重读变动源；这不等于真实发送或对敌对进程提供文件系统隔离。

每次尝试绑定同一个release_id和execution_id关联记录；已确认发送不得重复执行。结果不明先核实平台或接收记录，不自动重试。人工发送也要记录版本和回执，无法强制控制的部分如实标注。

### 4.8 变更重审、反馈与事件处置

条款、组合、参数、译文、附件、接收人、访问权限、用途、申请事实、规则版本等相关变化使审批失效；按影响关系追踪，不对不相关项目无差别清零。规则变化只有完成适用性复核后才能确认不影响旧审批。

异常公开时停止后续自动动作，在授权范围内限制访问、保存证据并通知责任人，分地区评估补救。删除链接不等于恢复新颖性；撤回或补申请效果须个案判断。事件的核实、专业处置和关闭需要独立记录，不能把重新审批当作事件已经消失。

## 5. 状态、失效与阻断

三类状态独立保存：文档可能已核稿，披露审批仍待签核；审批有效也不代表已经发送；已经发送也不代表标准获批或软件登记成功。

| 状态对象 | 允许的主要状态 | 关键转换依据 |
| --- | --- | --- |
| 专业内容审核 | 未开始、待补事实、审阅中、有条件意见、通过、不通过、失效 | 来源、版本和专业意见；未知、未检查不能转成通过 |
| 披露审批 | 草稿、待签核、条件待满足、可执行、拒绝、撤销、过期、失效 | 具体包、对象、条件及必需签核；条件满足后仍需执行前复核 |
| 执行 | 未执行、执行中、确认未发送、结果不明、已确认发送 | 实际回执／核实记录；超时不是确认未发送 |
| 事件 | 已报告、止损与核实中、专业处置中、已关闭 | 事实、责任人和有权决定；关闭不宣称恢复未公开状态 |

| 触发 | 系统规划行为 | 仍可交付 |
| --- | --- | --- |
| 未申请且拟公开需保留保护机会的技术 | 阻断该公开路线，转保护／披露策略判断 | 内部问题清单和候选稿 |
| 申请存在但内容支持、日期或地区安排不足 | 暂缓相关内容，不以申请号放行 | 支持缺口与可选处理方案 |
| 保密、材料权利或接收范围未知 | 按潜在公开或未授权处理，补证据 | 受控工作稿；不得含糊标为已授权 |
| 文件、对象或条件偏离审批 | 使审批失效并拒绝执行 | 差异记录与重审请求 |
| 无有权人、审批/规则服务不可用 | 保留草稿，不降级为自动同意 | 明确阻塞原因 |
| 发送结果不明 | 暂停重试，核实实际结果 | 待核实执行记录 |
| 误发、提前公开或权限扩大 | 启动事件流程，停止后续相关动作 | 事件证据及专业处理清单 |

## 6. 真实执行边界

SKILL.md中的要求只能约束建议流程，不能保证阻止宿主、插件、工具、用户或其他进程外发。现有及后续能力声明须区分：

1. **指导模式**：生成审批材料和人工交接清单；不声称技术阻断，未接管的手工操作由执行人负责记录。
2. **受控执行模式**：所有宣称受控的出口由权限层及适配器实施检查，工具调用、模型、检索、向量、图像、日志、遥测和附件均纳入数据路径清单；未覆盖出口不得标为已受控。
3. **离线模式**：宿主模型、索引、遥测和子进程的数据路径均有证据支持本地处理后才能如此标注；本地文件不等于本地推理。

不要求为规划先构建平台。若环境无法限制外发，先使用非敏感合成资料验证流程，不能让“用户承担风险”替代未实现的安全能力。数据保留遵循授权及适用义务；事件证据处于保全要求时，不因普通清理策略自动删除。
